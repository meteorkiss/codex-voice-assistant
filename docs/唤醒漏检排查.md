# 唤醒漏检排查

2026-09-08。本次处理的是喊“你好，声伴”没有唤醒，不是唤醒后的语音转文字错字。

## 已做的有限调整

将实际默认关键词阈值从 **0.5 降为 0.35**：`src/WakeListener.cs`、`src/wake_worker.py` 中的类默认值与命令行默认值保持一致。主程序未显式覆盖这个值，新启动的进程使用新默认；诊断阶段没有重启正在运行的声伴；随后于 2026-09-08 19:00:32 本地时间加载 0.6.7，已从运行时状态确认门槛为 0.35，原绑定与偏好保留。记录见 `work/tests/voice-create-live.json`。

降低门槛有少量离线收益，但可能增加真实环境中的误唤醒。**没有测试用户真人声音，不能宣布真人唤醒问题已经解决。**没有更改麦克风增益、AEC、采集启动顺序或问句 ASR 阈值。

改动前的两份源文件已保存在 `work/backups/before-voice-create-20260908-183158/`。安装时的模型 `manifest.json` 仍保留当时默认 0.5 的历史元数据；它不参与运行时阈值读取。

## 离线证据

只使用已有自拟合成音频：3 条正例（台湾晓臻、台湾晓雨、普通话晓晓）和 8 条反例，包括“你好，老板”“你好，怎么办”、半句、普通讲话、噪声与静音。未联网合成、下载、读取私人录音、打开麦克风或外放。

每档阈值运行 151 个内存变体，共 **453 次判定**。变体包括原音量及 -12/-24/-36 dB、固定 RMS 0.003 的粉红噪声、20/10/5/0/-5 dB 信噪比，以及故意剪掉唤醒词开头。混合后经过 PCM16 量化，变体音频不落盘。

| 测试组 | 0.35 正例检出 | 0.5 正例检出 | 0.65 正例检出 |
|---|---:|---:|---:|
| 仅改变音量 | 12/12 | 11/12 | 5/12 |
| 改变音量并加固定噪声 | 11/12 | 9/12 | 5/12 |
| 不同信噪比 | 11/15 | 9/15 | 4/15 |
| 完整唤醒词合计 | **34/39** | **29/39** | **14/39** |
| 故意剪掉开头，单独列出 | 7/18 | 7/18 | 2/18 |

每档阈值的 **94 个反例变体均未误触**。这些变体只来自 8 条合成反例且高度相关，不能据此估计真实房间里每小时的误唤醒次数。没有覆盖用户口音、远场混响、设备噪声、手机外放或实际 AEC 处理失真。

0.35 比 0.5 补回了 5 个完整正例变体：晓臻 -24 dB 加固定噪声、晓臻 -36 dB、晓臻 -36 dB 加固定噪声、晓臻 20 dB 信噪比，以及晓雨 -5 dB 信噪比。原始干净的 3 条正例，两档都能识别；不同噪声条件的结果并非严格随信噪比单调变化。

## 尚未解决的准备空窗

`WakeListener.Run` 每次启动新的 Python 进程，等其发出 `READY`，然后才打开普通采集设备或启动 AEC。三次仅工作进程准备测量为 **1.940、1.723、1.906 秒**，不含设备/AEC 准备。录音结束或监听恢复另有 **800 毫秒冷却**，因此恢复到能听见之间可能超过约 2.5 秒，实际仍受设备和电脑负载影响。

这是源码与离线进程测量支持的风险，不代表已证实它就是本次用户连续喊多次的唯一原因。准备期间的声音没有进入采集；现有 3 秒环缓冲从实际采集开始后才积累，不能补回此前丢失的音节。剪掉开头后的 18 个诊断变体，0.35 与 0.5 都只检出 7 个；降低门槛并没有补救这类丢失。

程序已经提供 `IsReady`，状态文字会显示“正在准备语音唤醒”；不能仅凭 `IsListening=true` 或声波显示就认为模型和设备已经就绪。输入框留有草稿、桥接正在发送/校验、其他进程占用麦克风时，也会按现有保护逻辑暂停唤醒。这些状态需要与用户喊话时刻对应，才能区分“没有在听”和“在听但没识别”。

本次不重构监听生命周期。后续如要减少空窗，应单独评估复用常驻 KWS 模型与设备释放策略，并重新验证麦克风保护、取消代次和 AEC 路由，不能简单放开麦克风保护。
