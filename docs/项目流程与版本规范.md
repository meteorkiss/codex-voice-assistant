## 角色与任务命名

| 角色 | 标题格式 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| 总控 | `总控｜声伴 vX.Y.Z · 范围` | 架构、需求边界、风险裁决、调度、审核结论与版本决策 | 不直接改产品代码、跑工程测试或代替程序部署 |
| 程序 | `程序｜声伴 vX.Y.Z · 范围` | 实现、定向回归、新鲜验证输出、候审提交；获准后上传与部署 | 不自行扩大范围、宣布审核通过、开下一版本或归档版本任务 |
| 审核 | `审核｜声伴 vX.Y.Z · 范围` | 每个重大迭代使用新的独立任务，只读审查候选并向总控报告 | 不改代码、不提交、不部署、不替程序修复 |

新建或接续任务时必须完成两步名称核验：先用正式任务命名接口持久化名称，再只读检查声伴生产候选列表中同一任务 ID 的名称。创建回执或聊天正文都不能代替该核验。OpenAI 的 [App Server 文档](https://learn.chatgpt.com/docs/app-server)说明 `thread/name/set` 用于持久化用户可见名称，并由 thread 的 list/read/resume 等读取；本项目仍以实际生产适配器的只读返回为最终现场证据。

## 单项交付与验收

每次只推进一个明确小项，执行顺序如下：

1. 记录用户需求、影响与可观察现象，先做根因分析。
2. 用真实缺陷边界写会失败的回归并看见预期失败；无法安全自动化的真人、设备或外部服务项，改为明确的手工验收步骤，不伪造失败。
3. 做满足该回归的最小修复，不夹带需求池中的其它功能。
4. 运行与风险相称的新鲜验证，记录命令、对象、实际输出和未覆盖边界。断言数量不能替代覆盖说明。
5. 程序提交完整候选 SHA；独立审核只读复核并向总控报告。
6. 总控决定返修或交用户验收。用户说“可以了”只接受当时明确的小项；如果上下文可能指向多项，先澄清。
7. 当前小项通过后，总控才可提出同版本下一小项；未经用户确认，不自动实现问题池中的下一项。

当前唯一已授权小项是 0.6.18 的免唤醒任务切换闭环。产品候选为 `e81673e36b3d1e70ad0c85a0d6551a13ef2c0d63`（基于首个候选 `d5255ded36948009f79cc4c58b4bf98fe787919c`）；审核与用户验收前，不启动桌面秘书或其它 0.7.0 功能。

## 收口、接续与归档

只有用户明确说“收口”才执行以下动作：

1. 汇总本版本已交付小项、候选/发布提交、验证、未验收项、生成物与风险。
2. 通过适用的工程门槛，并确认上传、部署、标签或 Release 的实际状态。
3. 创建下一版本的总控任务，持久化正式名称，并用声伴候选列表核对同一 ID；确认对方已经接手。
4. 只归档已确认属于当前版本且已完成的总控、程序、审核任务。不得删除聊天，不得归档其它项目、未完成或归属不明的任务。
5. 下一版本总控先汇总去重问题池并向用户确认计划；只有计划获批后才委派程序，不自动开始实现。

用户接受单个功能、审核通过、程序提交、上传或部署都不单独等于“收口”。任务归档也不代表真人声学、异机安装、公开发行或所有需求已验收。

## 版本规则

本项目采用 [Semantic Versioning 2.0.0 中文版](https://semver.org/lang/zh-CN/)的基本含义，并对 0.x 阶段作如下项目约定：

- 修复或小范围行为纠正：补丁号加一。
- 新功能或较大迭代：次版本号加一，补丁号归零。桌面秘书候选目标为 0.7.0。
- 1.0 只在公开行为契约稳定并经用户决定后使用。
- `alpha`、`rc` 仅在构建、升级与兼容性已核验后使用，不用来掩盖未定义范围。
- 根目录 `VERSION` 只表示代码实际完成版本；计划标题或新任务不能提前改变它。
- 候选用完整提交 SHA 标识。正式发布的同一版本内容不可替换；之后的修复必须使用新的补丁版本，不重写标签或公开历史。

## 问题池规则

所有已知需求和缺口先进入 `问题池.md` 去重。分类只能使用 `重要`、`普通`、`待定`，每项都记录：ID、用户原始陈述的来源日期/任务 ID、现象与影响、证据或复现、分类理由、状态、目标版本和验收证据。历史来源没有可核对逐字原话时，必须标为“来源转述”，不得补写伪引语。

进入问题池不等于进入当前版本。目标版本是候选安排，不是授权；当前小项未通过时不抽取下一项实施。

## 工程参考的使用边界

仅参考以下原始仓库或官方文档的工作原则，不安装、不执行第三方脚本，也不把外部模板当作本项目已完成证据：

- [obra/superpowers · systematic-debugging](https://github.com/obra/superpowers/tree/main/skills/systematic-debugging)：先复现并收集证据，再确认根因。
- [obra/superpowers · test-driven-development](https://github.com/obra/superpowers/tree/main/skills/test-driven-development)：先看见针对缺陷的测试失败，再做最小实现并通过。
- [obra/superpowers · verification-before-completion](https://github.com/obra/superpowers/tree/main/skills/verification-before-completion)：完成声明必须依据新鲜命令和实际输出。
- [obra/superpowers · requesting-code-review](https://github.com/obra/superpowers/tree/main/skills/requesting-code-review)：用明确基线/候选 SHA 请求独立复核，并处理审查反馈。
- [github/spec-kit](https://github.com/github/spec-kit)：既有项目采用增量式 specify → plan → tasks → implement → converge；规格清单不等于实现证据。
- [openai/skills · security-threat-model](https://github.com/openai/skills/tree/main/skills/security-threat-model)：风险分析基于仓库事实、边界和假设，区分运行时与 CI/测试环境。
- [openai/skills · gh-fix-ci](https://github.com/openai/skills/tree/main/skills/gh-fix-ci)：先读取 GitHub Actions 失败日志、总结并取得修复计划批准，再实施。
